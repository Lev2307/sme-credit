# frontend

React 19 + TypeScript на Vite, UI на Mantine 9. Одно приложение на две роли: кабинет клиента и кабинет андеррайтера. В Docker собирается и раздаётся через nginx, который заодно проксирует `/api` и `/admin` на бэкенд.

Клиент API (`src/api/`) генерируется orval из `docs/api/openapi.yaml`, руками его не правим. Токены и правила интерфейса описаны в [DESIGN.md](DESIGN.md).

Подробности в [docs/04-architecture.md](../docs/04-architecture.md), экраны и сценарии вытекают из [docs/01-research.md](../docs/01-research.md) и [docs/02-process.md](../docs/02-process.md).

## Запуск в Docker

Фронт собирается и поднимается вместе со всем стеком из корня репозитория:

```bash
docker compose up --build
```

Кабинет откроется на http://localhost:8080 (порт меняется переменной `FRONTEND_PORT` в `.env`). Образ двухступенчатый: Node собирает `dist/`, nginx его раздаёт и проксирует `/api`, `/admin` и `/static` на контейнер `backend`. Настройки nginx в [nginx.conf](nginx.conf).

В Docker отправленную заявку обрабатывает `worker` через Redis. Без Docker нужен либо запущенный Redis с воркером Celery, либо `CELERY_TASK_ALWAYS_EAGER=1` у бэкенда, иначе заявка после отправки так и останется «На проверке».

## Локальный запуск

Нужен Node.js 22 или новее. Бэкенд должен работать на `localhost:8000`, моки на `localhost:8090`: dev-сервер Vite проксирует на бэкенд `/api` и `/admin`, поэтому фронт и API живут на одном адресе и refresh-cookie работает без CORS.

```bash
npm ci
npm run dev
```

Кабинет откроется на http://localhost:5173. Тестовые учётки показаны прямо на странице входа.

## Команды

| Команда | Что делает |
|---|---|
| `npm run dev` | Dev-сервер на :5173 с прокси на бэкенд |
| `npm run build` | Проверка типов и сборка в `dist/` |
| `npm run api` | Перегенерировать клиент API после изменения `docs/api/openapi.yaml` |
| `npm run typecheck` | Только проверка типов |
| `npm run lint` | ESLint с правилами хуков и доступности |
| `npm test` | Компонентные тесты (Vitest + Testing Library, HTTP замокан через MSW) |
| `npm run e2e` | Сценарии Playwright против настоящего бэкенда на :8000. Перед первым запуском: `npx playwright install chromium` |

## Как устроен вход

- `POST /auth/login` отдаёт access-токен, refresh-токен бэкенд кладёт в httpOnly-cookie на `/api/v1/auth/`.
- Access-токен хранится только в памяти (`src/shared/api/token.ts`). После перезагрузки вкладки сессия поднимается запросом `POST /auth/refresh` по cookie.
- На ответ 401 HTTP-клиент (`src/shared/api/http.ts`) один раз берёт новый токен и повторяет запрос. Одновременные 401 делят один refresh. Если refresh не удался, данные прошлого пользователя стираются, и защищённые маршруты отправляют на вход.
- Маршруты `/cabinet` и `/underwriting` пускают только свою роль. Права на данные всё равно проверяет бэкенд.
- Клиента без компании кабинет сначала ведёт на `/cabinet/company`: ИНН, данные из реестров, привязка. Привязать компанию можно один раз, поэтому E2E-сценарии этот шаг не нажимают, его проверяют компонентные тесты.

## Как устроена анкета

- Черновик открывается мастером на `/cabinet/applications/:id`: сумма и срок, финансы, залог (только у продукта с залогом), документы, проверка. Одна форма react-hook-form на все шаги, каждый шаг проверяет только свои поля. Правила те же, что у бэкенда: лимиты продукта, залог, согласие.
- Автосохранение (`useAutosave`): через 0.8 с после последней правки, при смене шага и при уходе со страницы. В PATCH уходят только изменившиеся поля, сохранения идут строго по очереди. Если вкладку закрывают с несохранённой правкой, браузер переспросит.
- Документы загружаются сразу, каждый файл отдельным `multipart/form-data`. В OpenAPI этот эндпоинт описан как JSON, поэтому загрузка написана руками в `features/application-form/documents.ts`.
- На шаге проверки виден список того, что осталось, со ссылками на нужный шаг. Если бэкенд при отправке нашёл проблемы (`missing_fields`, `errors`, `missing_documents`), показываем его список.

## Как устроена страница статуса

- Отправленная заявка на `/cabinet/applications/:id` показывает этап на пути «подача → проверка → решение → подписание → выдача», что сейчас происходит и сколько обычно ждать. Тексты для клиента собраны в `features/application-status/copy.ts`: коды статусов, действий журнала и причин в интерфейс не попадают.
- Пока заявка у банка (`IN_REVIEW`, `UNDERWRITING`, `DISBURSING`), заявка и её история опрашиваются раз в 4 секунды. Статус входит в ключ запроса истории, поэтому при смене статуса история перечитывается сама.
- Дозапрос: вопрос банка, нужные документы (их можно только добавить, удалять в этом статусе бэкенд не даёт), ответ и по желанию исправленные выручка и платежи.
- При отказе видна причина простыми словами из последнего события журнала и кнопка новой заявки. Отменить заявку можно до подписания, после подтверждения в модальном окне.

## Структура

```
src/
├── api/            # сгенерировано orval
├── app/            # провайдеры, тема, маршруты, проверка роли
├── features/       # экраны по сценариям: auth, company, applications, catalog, application-form, application-status, дальше оффер
├── pages/          # простые страницы без своей логики
├── shared/
│   ├── api/        # axios с токеном и refresh, единый формат ошибок
│   ├── lib/        # хуки и форматирование
│   └── ui/         # каркас кабинета, общие компоненты
└── test/           # MSW-сервер и renderApp для тестов
```
