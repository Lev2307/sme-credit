# frontend

React 19 + TypeScript на Vite, UI на Mantine 9. Одно приложение на две роли: кабинет клиента и кабинет андеррайтера. В Docker собирается и раздаётся через nginx, который заодно проксирует `/api` и `/admin` на бэкенд.

Клиент API (`src/api/`) генерируется orval из `docs/api/openapi.yaml`, руками его не правим. Токены и правила интерфейса описаны в [DESIGN.md](DESIGN.md).

Подробности в [docs/04-architecture.md](../docs/04-architecture.md), экраны и сценарии вытекают из [docs/01-research.md](../docs/01-research.md) и [docs/02-process.md](../docs/02-process.md).

## Локальный запуск

Нужен Node.js 22 или новее. Бэкенд должен работать на `localhost:8000`, моки на `localhost:8090`: dev-сервер Vite проксирует на бэкенд `/api` и `/admin`, поэтому фронт и API живут на одном адресе и refresh-cookie работает без CORS.

```bash
npm ci
npm run dev
```

Кабинет откроется на http://localhost:5173. Тестовые учётки показаны прямо на странице входа.

## Команды

| Команда | Что делает |
|---|---|
| `npm run dev` | Dev-сервер на :5173 с прокси на бэкенд |
| `npm run build` | Проверка типов и сборка в `dist/` |
| `npm run api` | Перегенерировать клиент API после изменения `docs/api/openapi.yaml` |
| `npm run typecheck` | Только проверка типов |
| `npm run lint` | ESLint с правилами хуков и доступности |
| `npm test` | Компонентные тесты (Vitest + Testing Library, HTTP замокан через MSW) |
| `npm run e2e` | Сценарии Playwright против настоящего бэкенда на :8000. Перед первым запуском: `npx playwright install chromium` |

## Как устроен вход

- `POST /auth/login` отдаёт access-токен, refresh-токен бэкенд кладёт в httpOnly-cookie на `/api/v1/auth/`.
- Access-токен хранится только в памяти (`src/shared/api/token.ts`). После перезагрузки вкладки сессия поднимается запросом `POST /auth/refresh` по cookie.
- На ответ 401 HTTP-клиент (`src/shared/api/http.ts`) один раз берёт новый токен и повторяет запрос. Одновременные 401 делят один refresh. Если refresh не удался, данные прошлого пользователя стираются, и защищённые маршруты отправляют на вход.
- Маршруты `/cabinet` и `/underwriting` пускают только свою роль. Права на данные всё равно проверяет бэкенд.
- Клиента без компании кабинет сначала ведёт на `/cabinet/company`: ИНН, данные из реестров, привязка. Привязать компанию можно один раз, поэтому E2E-сценарии этот шаг не нажимают, его проверяют компонентные тесты.

## Структура

```
src/
├── api/            # сгенерировано orval
├── app/            # провайдеры, тема, маршруты, проверка роли
├── features/       # экраны по сценариям: auth, company, applications, дальше catalog и т. д.
├── pages/          # простые страницы без своей логики
├── shared/
│   ├── api/        # axios с токеном и refresh, единый формат ошибок
│   ├── lib/        # хуки и форматирование
│   └── ui/         # каркас кабинета, общие компоненты
└── test/           # MSW-сервер и renderApp для тестов
```
